# CodeAnvil v0.5.0

v0.5.0 moves every methodology-owned artifact under `.codeanvil/`, renames the GT
pair and the S1 design files, adds `codeanvil backup`, and tightens the S1, G1, S2
and G2 rework loops. Existing projects are not migrated.

## Breaking changes

- **GT and design moved under `.codeanvil/`.** New projects write the Build Package
  to `.codeanvil/GT/build_package.md`. The root `GT/` folder is no longer scaffolded.
  The S1 design is a single working copy in `.codeanvil/design/`.
- **GT pair renamed:** `G0_StRS.md` → `StRS.md` and `G0_SyRS.md` → `SyRS.md`, in
  `.codeanvil/GT/` and in the locked blueprints under `.agents/skills/`.
- **S1 design files renamed:** `S1_design.md` → `design/SDD.md`, and
  `S1_graph.html` → `design/dependency_graph.html`. They no longer live in
  `.codeanvil/report/<cycle>/S1_artifacts/`.
- **New `codeanvil backup` command.** `codeanvil backup S0|S1|S2|G2` copies the
  stage's current outputs to `.codeanvil/backups/<cycle>/<stage>_iter<N>/` with a
  `MANIFEST.yaml` (source paths and SHA-256 digests). Skills run it before they
  overwrite outputs and stop if it fails. A resumed pass finds its backup already in place
  and continues. It does not cover `src/` or `verification/`;
  use git for code.
- **Existing projects finish their current cycle on the old paths.** There is no
  migration: `codeanvil migrate` does not exist, and `codeanvil sync` does not move
  GT or design files. A project scaffolded before v0.5.0 keeps its old layout until
  its cycle closes. Only projects created with `codeanvil create` after the upgrade use
  the new layout.

## Features

- **G2 verdict split.** An unchanged FEEDBACK now routes by verdict: `Verdict: module
  defect` → `S2 must rework first. Run the S2 skill.`; `Verdict: design defect` →
  `S1 must rework first. Run the S1 skill.`
- **Bounded S1 and G1 rework.** A design rework writes a change set per changed ID
  (old decision, new decision, reason, interface-changed flag) and records the SDD
  digest. G1 reviews that change set, traces each changed contract along the
  dependency DAG, and produces an impact map (files to edit and paths to retest). An
  unexplained impact becomes an open finding (checklist row G1.16).
- **Bounded S2 design-defect rework.** S2 takes the latest G1 PASS impact map as its
  input. It revises the affected contract and stub first, then the owning module,
  preserves unlisted modules, and reruns the affected `PATH-*` and VL-1 tests before
  the full VL-0 floor.
- **S2 pause schedule.** S2 asks at the start of every iteration which pause schedule
  to use (per layer and module, per layer (recommended), or per service). It adds one
  pause after cross-service integration, before the `PATH-*` tests. Each pause takes
  `continue`, `rework` or `stop`, recorded as checkpoint lines. `stop` writes no
  iteration.
- **Module subagents (optional).** The S2 parent keeps the kit, bases, contracts,
  integration and the pauses. Each module can go to one subagent that returns changed
  files, commands and per-test results. The default concurrency is 1, and S2 works
  without subagents.
- **Telemetry collector.** `references/telemetry_collector.py` is a locked file that S2
  copies into `verification/telemetry/`. It writes JSON lines per VL run (timestamp,
  host profile, CPU and memory of the `run.sh` process tree (or `--pid`) and of the system,
  temperature, measurement source,
  collector version). It uses `psutil`, which is listed in the project's dev group.
  Without `psutil`, each psutil metric is reported as `unavailable` with a reason. It
  never reports zero for missing data. G2 rejects a constant or placeholder reading as
  measured evidence.
- **Backups in status.** `codeanvil status` prints the latest backup per stage, for
  example `Backups: S1 iteration 1 → .codeanvil/backups/<cycle>/S1_iter1/`.

## Install

```bash
codeanvil upgrade
```

Then scaffold a new project to get the new layout.

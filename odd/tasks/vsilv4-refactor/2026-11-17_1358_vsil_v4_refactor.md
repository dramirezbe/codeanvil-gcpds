## 3. Target architecture

### 3.1 Chain and cadence

```
S0 → G0(+Gate H) → S1 → G1 ─┬→ S2(slice 0) → G2(0) → S3(0) → G3(0) ─┐
                            │  ┌──────────────────────────────────────┘
                            │  └→ S2(k) → G2(k) → S3(k) → G3(k) ─→ … (k = 1..n)
                            └──→ S2(system) → G2(system) → S3(system) → G3(system) → Verified Prototype
```

- Slice 0: `INFRA-PLAN.md` — bases, verification kit, stubs, top-down + placeholder integration.
- Slices 1..n: module `PLAN.md` files, from `slice_backlog.py`.
- `system`: `INTEGRATION-PLAN.md` — contract tests, `PATH-*`, entry point, VL-1 path tests.
- Accepted deltas between slices: S0/G0 or S1/G1 `delta-sync` iterations before the next S2.

### 3.2 Project layout additions

```
.codeanvil/
├── plans/                          ← S2 is the only writer
│   ├── BACKLOG.md                  ← slices, module rows, status
│   ├── INFRA-PLAN.md               ← slice 0
│   ├── INTEGRATION-PLAN.md         ← system scope
│   ├── DELTAS.md                   ← delta log (P8)
│   └── <SUB-xxx>/<module_id>/PLAN.md
└── report/<cycle>/
    ├── S2.md  G2.md  S3.md  G3.md
    ├── S3_artifacts/test_run.md
    └── G3_artifacts/verified_prototype.md
```

### 3.3 Report contract additions (all chain reports)

Description starts with, in this order:

```
Based on: <predecessor> iteration <N>
Scope: slice <k> | system | delta-sync          ← S2, G2, S3, G3; delta-sync for S0/G0/S1/G1
Input: <project-relative path> sha256:<64 hex>  ← one per consumed input; directories end in "/"
Output: <project-relative path> sha256:<64 hex> ← stages only: what this iteration delivered
```

`Input:` lines drive staleness (`custody verify`, `status`). `Output:` lines are read by the next
gate only: it compares them with its own `Input:` digests, and a difference (a file edited by hand
between the stage and the gate) is an `open` finding, never a silent pass.

| Report | Required `Input:` lines |
|---|---|
| G0 | StRS.md, SyRS.md |
| S1, G1 | StRS.md, SyRS.md (+ SDD.md for G1) |
| S2 | SDD.md, each plan written this scope |
| G2 | SDD.md, BACKLOG.md, each plan of the scope |
| S3 | each plan of the scope |
| G3 | each plan of the scope, `src/`, `verification/` |

Digests come only from `codeanvil custody digest` (A3), pasted verbatim, never hand-rolled
one-liners or typed by the agent. `codeanvil custody verify` is the single checker; `status` calls
the same function (the UI is deferred, §0).

### 3.4 Verdicts and routing (v4)

| From | Line | Routes to |
|---|---|---|
| G0 | exit 1 | S0 |
| G1 | `FEEDBACK` / `Verdict: RFD` | S1 / RFD |
| G2 | `Verdict: plan defect` + `Modules:` | S2 (named modules only) |
| G2 | `Verdict: design defect` | S1 |

| G3 | `Verdict: RFD` | RFD |

G2 never offers RFD (§12.2): its question is `PASS` / `FEEDBACK`.

### 3.5 Cross-cutting rule: every hash goes through `codeanvil custody`

No skill computes, or tells the agent to compute, a SHA-256 by hand. Every digest the methodology
records is produced by `codeanvil custody digest` and checked by `codeanvil custody verify` /
`verify-manifest` (A3).

- **Scope:** every file under `templates/skills/` (the 9 v4 skills: S0, G0, S1, G1, S2, G2, S3,
  G3, RFD — `SKILL.md`, `references/`, `templates/`, `scripts/`), `templates/agents/`
  (`vsil-verifier.md`, `vsil-implementor.md`), `templates/AGENTS/TEMPLATE_AGENT.md`, and the
  bundled MCP skills under `templates/mcp/*/skills/`.
- **Forbidden:** any instruction or code that hashes outside `custody`: `hashlib`, `python -c …
  sha256`, `sha256sum`, `shasum`, `Get-FileHash`, `certutil -hashfile`, `openssl dgst`, a skill
  script with its own SHA-256, or asking the agent to "compute"/"recompute" a digest with the
  system's tools. Kit code generated by S3 (e.g. a golden-vector builder) never writes hashes into
  `manifest.md`; the `SHA-256` column is filled from `codeanvil custody digest --raw`.
- **Allowed:** naming SHA-256 as a field or column a document must carry (SDD §1.5 weights, §1.6
  vector table, golden manifest), as long as the skill says the value comes from `custody`.
- **Every skill that records or checks a digest** states it once, in its Hard Rules:
  *"Digests: run `codeanvil custody digest`, paste its output verbatim, never type or compute a
  hash; check with `codeanvil custody verify`."* Today that is S0, S1, G1 and RFD (C5); in v4 also
  S2, G2, S3 and G3 (D, E, F-2, G-a), plus `vsil-verifier` and `vsil-implementor`.
- **Exceptions (not methodology instructions):** `src/codeanvil/custody.py` (the only
  implementation), and the retired `templates/backups/` and `templates/no-tools-skills/`, which
  are never scaffolded.
- **Enforcement:** `tests/test_custody_rule.py` scans the scope above for the forbidden patterns
  and fails on any hit, and checks that every skill whose text writes `Input:`, `Output:`,
  `Module digest:`, `Build Package digest:` or a `SHA-256` column also contains
  `codeanvil custody`. A second assertion scans a freshly scaffolded project's `.agents/skills/`
  (`codeanvil create` in `tmp_path`), so path rewriting or shared assets cannot reintroduce one.

**A3 — `codeanvil custody`: one stateless owner of integrity** (D14)

Today SHA-256 is produced four ways and mostly never re-checked: `python -c "import hashlib…"`
one-liners (S0 `SKILL.md:30-31`, RFD `SKILL.md:87-89`, S1 `SKILL.md:112,144`), system commands
(`sha256sum`/`shasum -a 256`/`Get-FileHash`, G1 `SKILL.md:88-92`), agent-written kit scripts
(golden vectors, e.g. T0 `build_vectors.py`) and tool code (`backup.py:_sha256`). Only the S0↔RFD
Build Package digest has a consumer; the SDD Meta `G0 approved` row and the S1/G1 `SDD.md` digests
are information only, and G1's "S2 and G2 use it" has no reader. Golden manifests are never
checked against their files. `custody` replaces all producers and gives every recorded digest a
verifier.

- **State lives only in project files** (report `Input:` lines, `verification/golden/manifest.md`,
  backup `MANIFEST.yaml`, `.codeanvil/plans/DELTAS.md`). `custody` recomputes and answers; it
  writes nothing and never reads or writes the SQLite DB — no table, no cache (§8).
- `src/codeanvil/custody.py` (stdlib only):
  - `file_sha256(path)`: streamed SHA-256 of bytes.
  - `tree_sha256(dir)`: SHA-256 over sorted `relpath\0filehash\n`; file list from
    `git ls-files -co --exclude-standard -- <dir>` inside a Git work tree, else `rglob` minus
    `copy_ignore`, `node_modules`, `.venv`, `dist`, `verification/telemetry/`.
  - `verify(project_root, cycle) -> list[Finding]`: recomputes the latest iteration's `Input:`
    lines of every chain report (through A2's parser and H2's advances), every golden manifest and
    every backup `MANIFEST.yaml` of the cycle. One function; `status` calls it (A5). The UI does not, until its follow-up (§0).
  - `verify_manifest(manifest_md)`: parses the locked table (`File`, `SHA-256` columns) and
    compares each row with its file; also reports files present in the folder but absent from the table.
- CLI `src/codeanvil/CLI/commands/custody.py`, parser group, dispatch:

  | Subcommand | Output | Exit |
  |---|---|---|
  | `codeanvil custody digest <path>...` | Ready-to-paste `Input: <path> sha256:<hex>` lines (directories end in `/`); `--raw` prints the hex only | 0; 2 on a missing path |
  | `codeanvil custody verify [--cycle X]` | One line per finding: `stale-report`, `manifest-mismatch`, `backup-mismatch`, with path, recorded and current digest | 1 when any finding |
  | `codeanvil custody verify-manifest <manifest.md>` | Mismatched, missing and unlisted vectors | 1 when any finding |

- `backup.py:_sha256` is replaced by `custody.file_sha256` (A4).
- Skill call sites move in C5; a rule in each skill: **never type a digest, paste
  `codeanvil custody digest` output verbatim** — a mistyped or invented hash then shows up as
  `stale-report` on the next `status`.
- Tests: `tests/test_custody.py` — stable ordering, telemetry excluded, git/non-git parity, CLI
  output format, `verify` findings per kind, `verify-manifest` (match, edited vector, unlisted
  file, missing file), and an assertion that `custody` imports nothing from `codeanvil.db`.

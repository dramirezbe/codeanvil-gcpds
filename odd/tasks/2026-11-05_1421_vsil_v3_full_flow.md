## Specs

User requests quoted verbatim, in the user's language. Interpretations are marked **Assumption** and listed again under `## Assumptions to confirm`.

- **S1** — "S1 y G1: Será opcional el HW HAL y el lab si se va a utilizar solo el Mock HAL + etiquetado para todo el software."
  Scope: S1 declares a HAL mode. `mock-only` has no Real HW HAL, no lab procedures, calibration or tolerances, and no `hw_dependency: true` module. `mock+real` adds the Real HW HAL and cites the Build Package's lab inputs. G1 checks the Real HW HAL and lab inputs only in `mock+real`.

  Scope: the telemetry companion is mandatory in every design and every test run, lives in the verification kit, and never ships in the delivered software.

  Scope: one skill per stage or gate, short agent contracts that read a locked template (C7). A skill that does not work is thrown away and rewritten, not patched with extra machinery.

## Shared contracts (new, on top of C0–C11)

- **D1 HAL mode.** S1's design Meta carries `HAL mode: mock-only | mock+real`. Every later skill reads it from the design; nobody asks again.
- **D2 Two trees.** Code lives in the project root, outside `.codeanvil/`: `app/` is the delivered software (base, modules, and the Real HW HAL in `mock+real`), and `verification/` is the kit (Mock HAL, golden vectors and their `manifest.md`, telemetry companion, stubs, fake peers, drivers, tests). **Assumption A3.**
- **D3 Telemetry companion.** Mandatory in every design (S1 §1.7) and every test run (S2, G2). It is part of `verification/`, has no `SYS-*`, is not in the DAG and is never listed as module evidence.
- **D4 Golden vector manifest.** `verification/golden/manifest.md`, one row per vector: id, SHA-256, generation parameters, simulated condition, expected output. Changing a vector invalidates the evidence that used it.
- **D5 Levels by mode.** `mock-only` caps every claim at VL-1. `mock+real` allows VL-2, but each module or path still declares its level per cycle (S7).
- **D6 Design-defect route.** S2 and G2 never edit the design. A design defect is an iteration with `| HITL | FEEDBACK |` and the line `Verdict: design defect` naming the S1 sections to rework; S1 accepts it as a rework request, like a G1 FEEDBACK.

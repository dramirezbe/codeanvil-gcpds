# CodeAnvil 0.7.0 project contract for the UI

Scope: a **new project created with release `v0.7.0` (`2f08944`)**, followed
through the contracts of that release's active skills to G2. Audited 2026-11-11
using an isolated export of that tag and a freshly generated scaffold.
`methodology/test` projects are excluded from the evidence and requirements.
The UI implementation under review is `feat/ui` at `bec18c5`; it is being
mapped to the 0.7.0 project contract, not treated as part of the released tag.
This audit changes documentation only and adds no earlier-version compatibility.

This is the **pre-implementation audit**. The first implementation tranche
and its validation are recorded in the [UI plan](2026-11-10_2036_ui.md) and
current [UI README](../../../src/codeanvil/UI/README.md); the findings below
describe the baseline at `bec18c5`, not the later fixed code.

## 4. Gate and completion semantics the UI must preserve

- S0/S1/S2 `PASS` means **delivered**. G0 includes the deterministic validator
  **and human Gate H**; G1/G2 PASS are human decisions. G0's validator prints
  per-document and cross-document results to stdout without writing files;
  the skill includes its output in `G0.md`. Do not invent G0-X report files.
- A report is stale when its recorded predecessor iteration is older than
  that predecessor's latest iteration, including transitively. `status` follows
  the recorded `Based on` link; the UI currently follows a hard-coded chain
  and uses inequality, so it can disagree. In the release reader, a missing
  link does not set stale; it is not proof of a verified baseline.
- RFD is outside the chain: S1/G1/G2 can raise it. S2 records `Possible
  infeasibility` for G2. An unresolved RFD suspends work; an accepted deviation
  starts S0 in a new cycle and closes the old one. `Outcome: Withdrawn` releases
  the suspension into the normal rework route. S2/G2 never run in draft mode.
- A green fraction such as `6/6` is not a sufficient completion label. Show
  the human G2 verdict, stale/closed/draft/deviation context, and whether the
  final artifact is available. An old prototype file may remain after later
  FEEDBACK; its existence does not make the current cycle complete.
- VERIFIED covers VL-0/VL-1. VALIDATED applies only to actual VL-2 claims in
  `mock+real`, with the GT procedures, corrections and uncertainty evidence.
  `mock-only` caps claims at VL-1. An SSH target or a G2 PASS alone establishes
  no VL-2 claim. ML evidence remains future work in the active S2/G2 skills.
- A “Run prototype” control reads the project's documented entry point and
  endpoint; `run-demo`, service names and ports are not universal. Read them
  from SDD §0.5 and the G2 output §12. The UI's own default port is 8765 and
  its `--port` is configurable if a project's endpoint conflicts. A manual rerun does not
  append a G2 verdict; the agent skill and human still own that process.

**Shared reader defect to resolve before completion badges:** a probe with
iteration 1 PASS followed by iteration 2 without a HITL row returns iteration
2 **PASS**. `report_state()` takes the last verdict from the whole file, not
strictly the latest section. Track this as a core fix with regression coverage;
do not reproduce the behavior in a second UI parser or assume partial writes
cannot occur while an agent is working.

## 5. Telemetry, HIL and global state boundaries

The collector is `src/codeanvil/telemetry/collector.py`, invoked as
`codeanvil telemetry`. It is no longer a script copied under the S2 skill.
`psutil` is a tool dependency; methodology runtime base is now only `pyyaml`.
The default output is `verification/telemetry/telemetry-<timestamp>-<pid>.jsonl`;
the kit may set `<level>-<timestamp>.jsonl` through `--output`.

Each current sample has `collector`, `timestamp`, `monotonic_s`,
`measurement_source`, `host`, `process`, `system`, `temperature_c`, `counters`,
`counters_source`. CPU/memory readings distinguish the process tree and system;
`temperature_c` is `{value, sensor}` or `{unavailable: reason}`. Unavailable
is not zero. Counters are project-provided JSON, not a guaranteed metric set.
Samples have no standard cycle, level, target name or report-iteration field.
Preserve source filenames and cited run context; display unknown associations.
Plan a tolerant reader for a torn final JSONL line; `--fsync` is not implemented.

HIL target fields are `name`, `host`, `user`, `workspace`, `os`, `arch`, `device`,
`hil_policy`. **No SSH port field exists in the Target model**, despite the
credential CLI accepting `--port`: transport currently uses the default SSH
port. Keep that limitation visible rather than promising nonstandard-port
operation from a UI form. Global credentials live under
`~/.codeanvil-config/hil/<target>/` (`deploy_ed25519`, `exec_ed25519`, public
keys, `known_hosts`); project target configuration does not contain those keys.

The server implements `init_codeanvil`, `ssh_exec_cmd`, `ssh_exec_cmd_trusted`,
`code_sync`, `fetch_evidence`, with the `trusted` policy MVP. `guarded`/`locked`
and Windows provisioning are not working alternatives. MCP `init_codeanvil` emits a provisioning script;
it does not itself run that script over SSH. `fetch_evidence` retrieves only
`verification/telemetry/`, not reports or arbitrary artifacts.

The transport exists, but active S1/S2/G2 and `vsil-verifier` do not yet encode
the proposed target execution contract; the bundled `vsil-hil-usage` skill is
still a TODO. No active `run.sh vl2` / `measurement.json` machine contract exists.
Expose implemented infrastructure separately from future remote verification.

Global UI settings also include `~/.codeanvil-config/db/codeanvil.db`,
`runtime/` (shared skill-script venv, spec/user packages), and `mcp/<server>/`
(isolated server venvs). Catalog names are **`marconi`** and **`vsil_hil_mcp`**.
Global installation is distinct from project activation in `.agents/mcp.yaml`.

## 6. Release 0.7.0 versus the UI development branch

The branch still declares package version `0.7.0`, but includes changes after
the release. These must not be presented as released 0.7.0 capabilities:

| Capability | Tag v0.7.0 | Branch bec18c5 / UI implication |
|------------|------------|--------------------------------|
| Project paths, seven active skills, stage/gate artifacts and telemetry | Verified from the tag; contract tree above | These contracts are unchanged; use them as the UI project model. |
| Browser UI / `codeanvil ui` / `[ui]` extra / launcher registry | UI module is empty; command and extra absent | UI development exists only on the branch. It will consume 0.7.0 projects. |
| `credential-setup` CLI and automatic credential scripts | Absent | Added after the tag. A UI targeting the released CLI cannot require this command; defer its guided form or explicitly require the later tool build. |
| Bundled HIL packaging | Server source and catalog entry exist, but wheel force-include omits `templates/mcp` | Inclusion was corrected after the tag. Do not promise bundled-server installation from the release wheel based only on its catalog entry. |
| HIL `code_sync` | Destination uses the absolute workspace with the confined deploy key | rrsync destination correction is after the tag. Do not claim the release has that fix or a verified remote workflow. |
| Create folder validation | Release scaffold produces the documented layout | Extra folder containment validation is after the tag; it changes validation, not output names. |

For strictly 0.7.0 operation, the supported project mapping is the core flow,
GT/design/reports, verification kit, collector and optional configuration as
documented above. HIL configuration can be displayed, but remote readiness is
not established by a configured catalog entry. No full S0→G2 execution was
performed in this audit: delivered files are specified by the **0.7.0 skill
contracts**, not taken from a completed project of another version.

Release documentation also has internal drift: parser help says S2/G2 are
unavailable although their active skills ship, and the SDD inventory template's
short `HWC-001` examples differ from StRS inventory `HW-*` and full
`HWC-<SUB>-<NNN>` constraints. Use the shipped skill contracts and the GT
component/constraint distinction for the UI.

## 7. Review gates for the updated UI plan

- **T11 → T1:** inventory the 0.7.0 artifacts first; share state computation
  with status; fix latest-iteration verdict leakage. Test delivered vs human
  PASS, transitive stale, RFD close/withdrawal, DRAFT, empty cycles and partial reports.
- **T10:** Add existing project uses manifest validation and the existing sync
  operation; Create uses label, folder, parent and installed MCP choices, then
  the existing create operation (including manifest and DB), not scaffold alone.
- **T4:** direct navigation to Design, deviations, test run and Verified
  Prototype; scoped nested-artifact access, iteration browsing, Markdown,
  backup manifests/history and source-aware telemetry/log views.
- **T3/T6:** live process session and agent launch lifecycle; keep skill/human
  decision ownership. Follow with targeted watchers including telemetry data.
- **T7/T8/T9:** component-based gallery with UI-owned cache/override design,
  fixed workspace scrolling, then browser validation and native packaging.
  Image fields/cache paths are UI proposals, not existing GT/manifest schema.

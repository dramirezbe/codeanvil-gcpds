# Feature — CodeAnvil GUI: forge-themed workspace over the V-SIL methodology

Objective: a modern, forge-themed graphical **workspace** (VSCode/Photoshop-like,
no page scroll) that is a management and access surface over CodeAnvil — see a
project's V-SIL progress, reports and iterations; run every current CLI
capability (and more) from buttons; show the COTS hardware as real images; and
launch favourite agents/editors. It **reuses the CLI's Python logic in-process**
(never shells out to the `codeanvil` binary) through a FastAPI backend + a
WebSocket/PTY frontend. It displays and relays; it never replaces the harness or
adds an LLM.

Status: **implementation in progress.** Design brief lives at
`src/codeanvil/UI/README.md` (the spec of record). Visual reference approved by
the user: the "CodeAnvil Forge" style-tile artifact (v3), workspace shell + heat-
as-state language + HW gallery. User: *"Me parece totalmente correcto el diseño.
y un poco el posicionamiento de todo."* — design accepted; panel positioning may
get minor tweaks during the frontend task.

Branch under development: `feat/ui` (initial audit baseline `bec18c5`; delivery
commits recorded in L11). **Target project contract:
release `v0.7.0` (`2f08944`), newly scaffolded projects only.** The branch still
declares 0.7.0 but includes later code; its UI is not part of the release tag.

**Current-contract audit (2026-11-11):**
[`2026-11-11_current_project_ui_audit.md`](2026-11-11_current_project_ui_audit.md)
maps the 0.7.0 scaffold, shipped active skills, reports and delivered software.
Use it with the README for implementation. Earlier-version projects and
compatibility are excluded. The current acceptance fixtures are the five
synthetic projects in `methodology/test/v0.7.0-example-artifacts/` created
later in this session from release 0.7.0. The audit's §6 identifies

Delivery strategy: `ask-on-risk` (default), phased. Each phase below is its own

Test runners: `uv run --extra dev pytest` for tool/methodology checks, including
the UI backend. Run `pnpm test` and `pnpm build` from

Stack (confirmed): backend FastAPI (Python, default package dependencies); frontend

## Specs

User requests quoted verbatim, in the user's language (Spanish). Interpretations
are marked **Scope**. Corrections are noted where a later message revised an
earlier one.

- **S1 — project detection drives two modes.** Original (self-corrected):
  *"Que solo funcione en un proyecto inicializado, sino falla con warning de que
  no estás en un proyecto codeanil, esto se hace revisando el directorio la
  existencia de .codeanvil/project.yaml (corrige si me equivoqué)"*. Corrected by
  the user to: *"Si se ejecuta en un proyecto X sin codeanvil, hace fallback a la
  listo de proyectos + el botón para crea uno. Si se ejecuta en una carpeta que
  sí tiene codeanvil, aparece en la interfaz de trabajo"*.
  Scope: detect a project via `.codeanvil/project.yaml` using the existing
  `config/paths.find_manifest()` (walks up). No manifest → **launcher** mode
  (projects list + Create button + global config). Manifest → **workspace** mode.
  No warn-and-exit; the launcher is the fallback.

- **S2 — app, native on all OS, over WSL on Windows.** *"Debe de funcionar como
  una app más. [...] si quiero que sea de escritorio nativa en todos los OS
  (darwin, win, linux). Se puede usar lógica de ws para hablar con la terminal?
  Podemos hacer lógica para WSL? App en windows, pero usa WSL."*
  Scope: FastAPI monolith + WebSocket to a real PTY; works on Linux/macOS/Windows.
  Windows drives WSL (S9).

- **S3 — no hard-fail without an agent** (revises the original *"Falla si no hay
  un proceso de agente actual"*): *"No falla sin agente. Debe de hacer visible
  para el usuario que debe ejecutar un agente antes de querer chatear con él.
  Pero no es necesario para la vista de progreso e informes."*
  Scope: progress/reports/GT/design views never gate on an agent; only the
  chat/terminal shows a "launch an agent first" state when none is live.

- **S4 — expose all current functionality + more.** *"Quiero que investigues
  todas las funcionalidades actuales de no solo el CLI, sino de toda la
  metodología. Quiero una interfaz que me deje ver el avance, los reportes, las
  iteraciones, que me dé botones para ejecutar todas las funcionalidades actuales
  del CLI y +"*.
  Scope: see §12 of the README for the full inventory (progress board, reports &
  iterations, GT/design viewers, backups, telemetry, HIL targets, logs; run
  create/list/sync/status/backup/now/runtime/mcp/telemetry/init/upgrade; plus
  the `(+ new)` views). credential-setup belongs to a later tool build and is
  deferred outside the strict 0.7.0 baseline.

- **S5 — reuse CLI code, no shelling out.** *"Debe de reutilizar el código del
  CLI, sin usar el CLI por debajo, dejarlo sin adherencia a llamar al CLI por
  debajo"*.
  Scope: backend imports the logic layer in-process; no `subprocess` to the
  `codeanvil` binary for logic the tool already does in Python. Exceptions:
  launching external agents/editors and running `verification/run.sh`.

- **S6 — self-sustained backend that serves the UI.** *"Backend autososstenido
  que muestra la UI (esto depende si la hacemos browser-based o compiado a
  escritorio con tauri por ejemplo)"*.
  Decision (from S7 "vs"): MVP **browser-based** (`codeanvil ui` → FastAPI →
  system browser); ship target **Tauri** (FastAPI as PyInstaller sidecar).
  PyWebView is the pure-Python middle ground; Electron last resort.

- **S7 — packaging comparison.** *"No sé, haz un vs con varias opciones"*.
  Scope: the "vs" is captured in README §4; resolved as S6.

- **S8 — agent/editor sidebar, two groups, install scan.** *"Botones para
  ejecutar tus agentes o IDE favoritos con iconos de cada uno (vscode, opencode,
  claude, pi, codex)"* and: *"Recomendaría tener una barra lateral con la lista
  de IDEs + agentes. [...] separación de necesita terminal vs no necesita
  terminal. [...] Sin terminal: Codex desktop, Opencode desktop, claude desktop,
  vscode, jetbrains. Necesita terminal: codex, claude, opencode, pi. Si es un
  proceso de terminal deberíá de haber una lógica inicial que sea abrir una
  terminal + abrir la app (todos en la ruta del proyecto seleccionado). Puede
  haber un escaneo de lo que hay instalado, y dejar opaco lo no instalado. Si se
  le da al botón se le avisa al usuario que se va a instalar yu se instala el
  paquete solo si no necesita sudo (la mayoría de veces no). Se hace un source
  ~/$SHELL porsiaca"*.
  Scope: sidebar in two groups (no-terminal GUI apps vs terminal CLI agents);
  terminal agents open a terminal + the agent in the project path (the PTY the
  chat mirrors); scan installed → grey out missing; click-to-install only when no
  sudo is needed; `source` the shell rc after install.

- **S9 — WSL compatibility.** *"Alguna compatibilidad para WSL. Si se detecta
  wsl, se abre en segundo plano y se escanean las apps de agentes que haya.
  Después de eso seríá normal para el usuario, pero en segundo plano se carga wsl
  primero, y luego se ejecuta el app"*.
  Scope: on Windows, if WSL is detected, start the distro in the background, scan
  agents inside WSL, then run normally.

- **S10 — editable launcher YAML.** *"En un .yaml facilmente editable con todo lo
  que ya hablamos. Para yo poder cambiar rápidamente los comandos de instalación
  de cada uno de los CLI. Para compatibilidad de windows, se hace por winget si
  es posible, sino warning al usuario que lo instale a mano"*.
  Scope: a keyless, editable YAML with detect/launch/install per OS; Windows
  installs prefer `winget`, else warn the user to install manually (README §9).

- **S11 — live refresh via watchdog.** *"Con watchdog a todos los documentos que
  no sean código del proyecto. Si cambia (se guarda o cambia de SHA) se relee
  solo ese archivo y se refrezcan los items relacionados con ese archivo"*.
  Scope: watch the non-code `.codeanvil/` docs (report/GT/design/backups/
  project.yaml/audit); on change (save or SHA differs) re-read only that file and
  refresh only the bound UI items via WS push. No full rescans.

- **S12 — HW COTS image gallery, public API, no key.** *"Agrega la funcionalidad,
  API pública, nada de api-keys."* and: *"Quiero agregar que muestre imágenes de
  todos los componentes del HW COTS, que se traiga una HackRF y una RPI por
  ejemplo."*
  Scope (README §12.1): a card per `HWC-` component; images from **Wikidata
  `P18` → Wikimedia Commons** (keyless); cache into `.codeanvil/`; author override
  via `HWC-`/`project.yaml`; forge placeholder fallback; backend-side fetch (only
  the public component name leaves the machine).

- **S13 — workspace, no page scroll.** *"Quiero que no sea una página que toque
  hacer scroll. Quiero un ambiente de trabajo como photoshop, autocad, vscode,
  no sé. Algo que se sienta más ambiente de trabajo, que no necesite scroll para
  ver todas sus opciones. El único scroll que va a haber es el del chat y en los
  reportes."*
  Scope: fixed app shell (topbar / activity rail / side panel / canvas / right
  dock / status bar); only the chat and reports panels scroll. On phone width it
  may stack and flow (no horizontal scroll).

- **S14 — modern forge theme.** *"Interfaz moderna (inspirada en una forja, fuego
  de forja, etc. Un buen inicio puede ser un estilo tipo el videojuego WoW pero
  dandole una vuelta profesional)"*.
  Scope: approved style-tile — heat = state (ember active, steel-cyan quenched),
  shape voice (rounded plates / hard-edged billets), 8px scale, steel hairlines,
  light + dark, `prefers-reduced-motion`. "WoW-rich re-tuned professional".

- **S15 — CLI capabilities presented as real UI workflows.** *"Yo no quería un
  CLI actions tan plano. Yo quería funcionalidades ya definidas listas. Por
  ejemplo: codeanvil list ya lo hace la UI solita mostrando la lista de
  proyectos; codeanvil status se usará después; codeanvil sync: un botón que me
  deja escoger una carpeta de manera interactiva de mi sistema, y la dejará en
  la lista de proyectos. O sea yo quería las funcionalidades del CLI pero como
  UI normal, y que tenga sentido. [...] deja la funcionalidad de ejecutar CLIs,
  pero agrega al plan esto."* **Scope:** feature-oriented workflows are the
  primary user experience and the generic CLI action page remains as an
  advanced fallback. `list` stays the launcher project list; `status` stays the
  workspace progress board; `sync` gets an **Add existing project** button
  backed by a native directory picker, manifest validation and DB registration;
  `create`, backup, runtime, MCP, telemetry, HIL setup, init and upgrade get
  purpose-built contextual workflows. `now` is an internal utility. Commands
  requiring an interactive terminal use PTY.

  **MCP flow:** the launcher presents the MCP servers shipped in CodeAnvil's
  configuration in a marketplace-style catalog, with installed state and an
  install action. Installation remains global and uses the existing MCP
  lifecycle. The project creation wizard offers installed servers to activate
  for the new project; activation writes the project's MCP manifest, agent
  configuration and server skills. This is a local catalog, not a remote
  marketplace. Global installation and project activation are separate steps.
  **Reuse boundary:** `server_rows()`, `doctor()`, `install_mcp_server()`,
  `cmd_create()`/`scaffold_project()` and `enable_server()` already implement
  the catalog data, health check, installation and project wiring. Deliver
  this workflow in the UI package through the existing in-process action
  adapter or UI routes; no CLI, schema, manifest-format or MCP-core changes
  are planned.

- **S16 — self-contained global installation.** *"Pregunta. Cómo está conectado
  las dependencias de la página? Quiero que todo sea autocontenido en codeanvil
  global. Que al hacer \"codeanvil init\" ya instale todo"*.
  **Scope:** supersedes the optional Python `[ui]` dependency group. The normal
  global tool installation includes the web backend and prebuilt frontend,
  including fonts. `init` prepares and validates the UI alongside the existing
  DB/runtime setup, preserving registrations and editable launcher settings.
  End users need no Node, pnpm, frontend build or external font CDN. MCP servers,
  coding agents and optional native OS dialogs retain their existing boundaries.

### Execution order and acceptance after the audit

T11 defines the read model and T1 provides shared state operations. These
precede completion labels and the expanded T4 views. T10's first sync/create
workflows can progress independently once they use the audited manifest,
identity and registration contracts. Then T3/T6 provide live sessions, T4
adds targeted refresh, T7/T8 finish the workspace and T9 closes packaging.

**First implementation tranche delivered (2026-11-11).** Three subagents owned
the shared state/artifact reader, project workflow backend, and workspace
frontend. The parent integrated the routers/forms, CI and browser checks;
the workflow agent independently reviewed the reader. T11 is complete; T4,
T8 and T10 have the delivered portions shown above. PTY/agent sessions, live
watching, telemetry/gallery surfaces and desktop packaging were not part of
this first tranche.

- **State:** an empty 0.7.0 scaffold opens; the project's cycles are selectable without
  changing `cycle:`; DRAFT is not counted as a gate; RFD closure/withdrawal and
  transitive staleness agree with status. A partial latest iteration cannot
  inherit a previous PASS. No new UI gate orchestrator or verdict writer.
- **Artifacts:** current GT/design plus nested test run, prototype and deviation
  documents are reachable at the exact 0.7.0 paths. All acceptance fixtures
  come from this release's scaffold/skill contracts. Working GT/design are
  shared across cycles and must not masquerade as a per-cycle snapshot.
- **Delivery:** show S2 services from the SDD Toolchain and the exact §0.5/§12
  entry point, endpoint and stop instructions. `src/<package>/`, `run-demo`,
  ports and validation claims must not be inferred from the example project.
- **Evidence:** verification/telemetry JSONL is read separately from source;
  unavailable sensors and unknown run/cycle/target associations stay explicit.
  A target declaration or transport action never creates a VL-2 claim.
- **Workflows:** creation completes scaffold + identity + DB registration;
  sync updates by UUID. MCP global install and project activation stay separate.
  All exposed surfaces need a useful empty/error state and focused verification.

HIL is a separate dependency beyond the strict 0.7.0 baseline: the tag omits
bundled MCP sources from wheel packaging, predates the rrsync destination fix,
and has no credential-setup command. Active S1/S2/G2/verifier contracts have
not adopted remote execution, and vsil-hil-usage is still a placeholder.
Read-only target/configuration/audit views can use present data; guided setup
needs the later tool build. Automatic remote G2, run.sh vl2 and measurement.json
remain future work. See the audit's release-versus-branch table.

High-risk watch: T3 (PTY/process spawning, shell env), T6 (install actions,
sudo detection, WSL process control, launching external programs) — Risk items
to confirm at implementation; each gets its own commit and the verification gate.

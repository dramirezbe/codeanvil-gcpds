Superseded by the implemented [relaxed HIL operation and pre-hardware review](2026-11-11_2042_hil_relaxed_refactor.md).

The delivery log below preserves historical evidence for the first implementation.

Objective: let a V-SIL project run its verification kit on a **real compute unit** (Raspberry Pi, Jetson, an x86 box, or the dev host itself) instead of only the developer's machine, so VL-0/VL-1 become *processor-in-the-loop (PIL)* evidence and VL-2 *hardware-in-the-loop (HIL)* measurement becomes machine-captured rather than human-pasted. ## The hard problem — how the agent gets SSH access (S4)

The MCP server runs as a subprocess the agent runtime spawns (`codeanvil mcp run vsil_hil_mcp`). `ssh_exec_cmd(cmd)` must authenticate to the target. The design must avoid three failure modes:

1. the agent holding raw credentials,
2. coupling HIL to the user's personal SSH identity (a rogue agent could then reach every host the user can),
3. the agent silently gaining a foothold on an arbitrary machine.

### Principle: the server is the credential **custodian**; the agent gets a **capability**

The agent calls `ssh_exec_cmd(cmd)` and receives raw stdout. It never sees the key, never gets an interactive shell it controls. The capability is "run this one command on the *declared* target," nothing more. Credentials never enter the agent's context.

### Dedicated HIL identity, isolated from the user

Keys are generated per target under `~/.codeanvil-config/hil/<target-id>/`, **not** `~/.ssh`. Owned by the HIL subsystem. Blast radius of a misbehaving agent is limited to *declared targets*, never the user's whole SSH reach.

### Two keys, two jobs — confinement lives on the target

| Key | Used by | Target-side confinement |
|-----|---------|-------------------------|
| **deploy key** | `code_sync()` | `authorized_keys` forced-command `rrsync <workspace>` (the hardened restricted-rsync wrapper that ships with rsync). Can **only** rsync into the workspace — no shell, no other path. |
| **exec key** | `ssh_exec_cmd()` / `ssh_exec_cmd_trusted()` | maps to an **unprivileged** target user in a dedicated workspace; sudo governed by the `hil_policy` dial. |

Passphraseless keys are acceptable **because** confinement is target-side (forced-command / unprivileged user), not key-side. A key that can only drive `rrsync` or a sandboxed user is safe to use non-interactively.

### First contact is human-consented — the agent never bootstraps its own foothold

This is the core of "cómo dar acceso ssh al agente." On first contact `init_codeanvil()` has **no access yet**. It cannot add itself to a fresh machine. Instead it emits a **provisioning bundle** the human applies once on the target:

- create the unprivileged user + dedicated workspace,
- install the two public keys with their restrictions (`rrsync` forced-command for deploy; confined user for exec),
- install CodeAnvil and run `codeanvil runtime sync`.

Apply options (one decision to confirm, A2):
- **(a) printed script** the human runs on the target once — zero credential transfer, fully explicit; **(recommended)**
- **(b)** the human does a single `ssh-copy-id` of the exec key with their own credentials, then init proceeds over that channel.

Either way the **human is the bootstrap authority**; the MCP is never handed the power to enroll new machines on its own.

### Host-side command classifier (S3 policy) — honest about what it is

Every command is classified in the server before any SSH and routed to one of **two doors** (full detail under *Privileged execution* below):

- **`ssh_exec_cmd` (ALLOW, auto):** read-only shell (`ls`, `cat`, `stat`, `find`, `uname`, `df`, `free`, `/proc/*`), the **entire `codeanvil …` CLI**, and `python`/`pytest <script>` inside the workspace. If it sees `sudo` (or another privileged marker) it **refuses** and redirects to the privileged door — it never runs a sudo itself.
- **`ssh_exec_cmd_trusted` (the privileged door):** carries `sudo`/mutating commands; the runtime's native prompt on this distinct tool is the human's approval.
- **Audit:** every call logged (target, cmd, exit) to `.codeanvil/hil/audit.log` — attributable and replayable.

**Caveat recorded by design (same honesty as the paper's verified/validated split):** allowing `python`/`pytest` and the full `codeanvil` CLI *is arbitrary execution* — `codeanvil python evil.py` can do anything the confined user can. The classifier is **not a sandbox**. What it genuinely buys: (1) audit, (2) a distinct, separately-approved door for every privileged action, which stops the realistic LLM failure mode — accidents and scope-creep — not a determined adversary. The actual blast-radius limit is the **target OS isolation** (unprivileged user, workspace, rrsync forced-command, the `hil_policy` dial). Three layers, each honest: `authorized_keys` protects the rest of the machine; the classifier stops accidental scope; OS isolation is the real jail.

### Skill vs server — teach, don't enforce

A skill ships with the server (`copy_mcp_skills` copies `templates/mcp/vsil_hil_mcp/skills/*` into `.agents/skills/vsil_hil-*`, marconi pattern) to **teach** the agent: the deploy→run→fetch loop, which tool to call when, the VL-0/1/2-on-a-target workflow, and how to react to a `use_trusted` redirect (re-issue the command through `ssh_exec_cmd_trusted` and present it). **It is guidance, not a control.**

The **ASK classifier and the tool implementations live in the server code**, never in the skill. Reason: a skill is markdown the agent reads — it can be ignored, misread or manipulated; security that depends on the agent choosing to obey text is not security. Every `ssh_exec_cmd` passes through the classifier *inside the server* before any SSH happens, regardless of the agent's intent. The tool **schemas** are advertised by the server over MCP at connect time — the agent discovers `ssh_exec_cmd(cmd)` etc. automatically; the skill describes them, it does not define them. Mirrors how gates already split: enforcement = code (G0 script), contract = SKILL.md. The skill makes a well-behaved agent a good citizen; the server makes a misbehaving one harmless.

### The approval flow — how a privileged command runs

**Constraint that shapes the whole design:** the MCP server is a subprocess; it **cannot draw UI and cannot know on its own that a human said yes**. So approval must be enforced by a layer that *can* gate — the host runtime's native tool-permission prompt. The server's job is to make the privileged action *surface as its own distinct tool call carrying the exact command*, so the prompt the human sees is the command that will run.

Four parties, clean roles: the **human** decides · the **runtime** enforces (its native permission prompt) · the **agent** mediates (picks the door, presents the command) · the **server** classifies and executes.

The flow:
1. Agent calls `ssh_exec_cmd("sudo …")`. Server classifies → privileged → **refuses**, returning `{status: "use_trusted", command, reason}`. Nothing runs.
2. The skill tells the agent to re-issue it through the privileged door and present it: *"the target needs `<command>` because `<reason>`"*.
3. Agent calls `ssh_exec_cmd_trusted("sudo …")` with the **same exact command**. Because this is a distinct tool, the runtime shows its **native permission prompt with that command** — approving the prompt *is* the human's yes, enforced by the host, not by trusting the agent. No swap window: the command in the prompt is the command the server runs.
4. Human approves ⇒ server runs it **once**, verbatim, over SSH, returns raw stdout, under the target's `hil_policy` (passwordless sudo in `trusted`; password-custody in `guarded`; wrapper in `locked`). Human declines ⇒ nothing runs.

So "si apruebo, ¿qué pasa?": the `ssh_exec_cmd_trusted` call goes through the host prompt, the server runs exactly that command once and returns the output. Nothing else runs.

**Human-only** stays narrow: first-contact provisioning (the one root bootstrap) and **physical** faults (antenna, USB power, RF) — the agent names the symptom, cannot fix them. Everything else privileged is the `ssh_exec_cmd_trusted` door above; the human approves a prompt, never SSHes in to type.

**Non-interactive / sandbox:** no human to approve ⇒ the host denies the `ssh_exec_cmd_trusted` call ⇒ no privilege in automation. Correct by default.

**Audit:** both the refusal and the executed trusted call land in `.codeanvil/hil/audit.log` with target, command and exit.

### Privileged execution — a per-target policy dial (simple by default)

An earlier draft hardcoded a package + command allowlist in a root-owned wrapper. **Too rigid** — a fixed vocabulary cannot anticipate what a project needs. Replace it with a **coarse classifier + one human approval per privileged command**, and keep the strict wrapper only as an *optional* mode. One field per target in `project.yaml`: `hil_policy: trusted | guarded | locked`.

The classifier is **simple — no package lists, no command vocabulary** — and routes to one of **two doors**:

- **ALLOW — `ssh_exec_cmd` (auto):** read-only; `codeanvil` / `uv` / `python` / `pytest` inside the workspace. If the classifier sees `sudo` (or another privileged marker) in a command sent here, it **refuses it outright** — no run, no prompt — and tells the agent to use the privileged door. The auto tier can never carry a sudo.
- **TRUSTED — `ssh_exec_cmd_trusted` (the only privileged door):** the sole tool that may carry `sudo`/privileged commands. It is a distinct tool, so the runtime shows its **native approval prompt with the exact command** — that prompt is the human's yes (the host must not blanket-allow this tool). The server runs **any** command passed here, once, verbatim, audited. Any command — not a fixed list. This is the flexibility.

Modes (pick per target):

- **`trusted` — default, recommended for a lab box you own and can reflash.** The confined user has passwordless sudo; privileged commands go through `ssh_exec_cmd_trusted` (one approval, verbatim, audited); `ssh_exec_cmd` bounces any `sudo` it sees. Simplest and most flexible. **Honest residual:** the bounce is a *string* gate on the command line — it stops a direct `sudo`, but **not** a `python`/`pytest` script (ALLOW) that calls `sudo` *internally*, because the server never sees that sudo and it succeeds silently under passwordless sudo. Since the agent authors the deployed code, `trusted` does **not** actually contain a determined/compromised agent — it is a convenience + audit gate on a box you accept is reflashable.
- **`guarded` — same `ssh_exec_cmd_trusted` door, but closes the indirect hole.** No passwordless sudo. The MCP **custodies the sudo password** (same trust as the SSH key it already holds) and supplies it ONLY to a command approved through `ssh_exec_cmd_trusted`; the agent and its scripts never have it. A stray `sudo` inside a deployed script now **fails** for lack of password — the one mode that actually stops the `python → sudo` indirect path, still with **no wrapper, no allowlist, any command**.
- **`locked` — the scoped wrapper, for a shared / long-lived / production-ish target.** Root-owned validating wrapper, but its allowlist is a **policy file the human edits in the project** (packages + command patterns), not hardcoded in the script — so still configurable. Most restrictive; use only when the target matters.

**Who sets up the box?** First-contact provisioning is the one human-consented root moment (installs the confined user, keys, and — in `guarded`/`locked` — the password custody or the wrapper). After that the agent works within the chosen mode and the human never SSHes in to type a command.

The point: **the wrapper is the strict end of a dial, not the mandatory mechanism.** Default (`trusted`) is as simple as it gets — general sudo gated by one human approval per privileged command, nothing hardcoded.

## Architecture

### Topology — the MCP is for REMOTE hardware only

`vsil_hil_mcp` exists to reach **hardware external to the host over SSH**. Running commands on the *local* host through an MCP is pointless indirection — the agent already executes locally through its normal tooling (`run.sh`, `codeanvil telemetry`, the shell), gated by the runtime's own permission prompts. So the MCP is **remote-only**:

| Case | HW location | Harness path |
|------|-------------|--------------|
| **PC→SDR (local)** | SDR on the control host | **No MCP.** The agent runs `run.sh` / `codeanvil telemetry` directly on the host; the runtime's native prompts gate privileged commands. |
| **SDR→RPi (remote)** | SDR on a remote UC | **`vsil_hil_mcp`** — the ssh/rsync proxy, credential custody, the two-door classifier and the `hil_policy` dial. |

The **delivered code is identical** either way — the Real HW HAL opens the SDR on whatever machine it runs on; the HAL port abstraction does not care. Only the **harness transport** differs: direct locally, MCP-mediated remotely. Consequence: the whole SSH-custody / two-door / `hil_policy` / sudo machinery below is **remote-only** — it exists because remote execution needs a credential custodian and a gate across the SSH boundary; locally the host's own permission model already provides that.

A **remote target** is persisted in `.codeanvil/project.yaml` under a `targets:` block (host, user, key paths, workspace, os, arch, CodeAnvil version, declared SDR device). No remote target declared ⇒ local path, no MCP. Remote target OS: Linux \| Windows; out of scope: no-OS (bare-metal MCU).

### `vsil_hil_mcp` tool surface (thin proxy)

All tools operate on the declared **remote** target; the local (PC→SDR) case uses no MCP.

| Tool | Does |
|------|------|
| `init_codeanvil(target)` | Probe → emit provisioning bundle (human-consented) → install CodeAnvil + `runtime sync` on the remote target → install project deps → register in `project.yaml`. Refuses non-Linux/Windows. |
| `ssh_exec_cmd(cmd)` | Run `cmd` on the declared **remote** target; return raw `{stdout, stderr, exit_code}` untouched. **The interface** — telemetry, tests, probes go through it. Read-only + `codeanvil`/`uv`/`python`/`pytest` in the workspace; **refuses `sudo`** and redirects to the trusted door. |
| `ssh_exec_cmd_trusted(cmd)` | The only privileged door: carries `sudo`/mutating commands. Distinct tool ⇒ the runtime's native prompt on it (showing the exact command) is the human's approval. Runs once, verbatim, audited, under the target's `hil_policy`. |
| `code_sync()` | rsync host→target workspace (deploy key / `rrsync`), excludes `.git`, `__pycache__`, `verification/telemetry/`, `.env`, `*.key`, `*.pem`. |
| `fetch_evidence()` | rsync target→host of **only** `verification/telemetry/` — the folder the collector writes its per-run `telemetry-*.jsonl` into (confirmed in `telemetry_collector.py`: default `Path.cwd()/verification/telemetry/`), plus the future VL-2 `measurement.json`. So G2 reads the evidence on the host. |

### MCP manager integration — bundled, not cloned (A1)

The current manager (`src/codeanvil/init/mcp.py`) clones an external `repo` at a pinned `ref` (marconi = `gr-mcp`). `vsil_hil_mcp` is **core V-SIL infra** that must version-match CodeAnvil (collector parity is a verification requirement) and wants the bundled-collector semantics. **Decision (recommend): first-party / bundled server**, shipped inside CodeAnvil (`src/codeanvil/mcp/hil/`), installed without a clone — `install_dir` resolves from the installed package, venv built from CodeAnvil's own deps. `config.yaml` gets an `mcp_servers.vsil_hil_mcp` entry marked `source: bundled` (vs the implicit `repo:` of marconi); the manager learns to skip `_checkout_ref` for bundled servers. Everything else (launcher `codeanvil mcp run`, per-agent configs, enable/disable) is reused unchanged.

### Naming convention — `vsil_*` for methodology-owned servers

Methodology-owned MCP servers (first-party, shipped and version-matched with CodeAnvil) are prefixed **`vsil_*`** — this one is `vsil_hil_mcp`. External / third-party servers keep their own names (e.g. `marconi`). The prefix is how the manager and the user tell a first-party/bundled server from a cloned one at a glance.

### Project wiring — same MCP lifecycle as marconi

`vsil_hil_mcp` lives in the **inventory** (`templates/config.yaml` `mcp_servers:`) and uses the existing manager verbs unchanged:

| Step | Command | Effect |
|------|---------|--------|
| catalog | — | entry in `config.yaml mcp_servers.vsil_hil_mcp` |
| install (global, once) | `codeanvil mcp add vsil_hil_mcp` | `install_mcp_server()` → `~/.codeanvil-config/mcp/vsil_hil_mcp/` + venv + probe |
| see it | `codeanvil mcp list` | `server_rows()` row: installed?, ref/bundled, pinned |
| wire into a project | `codeanvil create --mcp vsil_hil_mcp` **or** `codeanvil mcp enable vsil_hil_mcp` (inside the project) | `generate_agent_mcp_configs()` writes `.mcp.json`, `.vscode/`, `opencode.json`, `.codex/`, all calling the launcher `codeanvil mcp run vsil_hil_mcp` (no absolute path) |
| unwire / remove | `codeanvil mcp disable` / `codeanvil mcp remove` | as marconi |

**Opt-in**, like marconi — not auto-wired on `create`, because not every project does HW validation.

**Agent interface = pure MCP, not the CLI.** The agent uses the server by calling its tools over the MCP protocol (`ssh_exec_cmd(...)`, `code_sync()`, …), never by typing a `codeanvil` shell command. The CLI appears only (1) once, human-side, to install and wire the server (`mcp add` / `create --mcp` / `mcp enable`), and (2) as the launcher `codeanvil mcp run vsil_hil_mcp` that the runtime spawns from the generated config — invisible to the agent's workflow. A `codeanvil` command that runs *on the remote target* (e.g. `codeanvil telemetry`) is relayed there by the server through `ssh_exec_cmd`; the agent still only issues an MCP tool call. The wiring is agent-agnostic — `.mcp.json` (Claude Code), `.vscode/`, `opencode.json`, `.codex/` — so whichever harness is preferred talks to the same stdio server.

Two deltas from marconi:

1. **Install is bundled, not cloned** (A1): `mcp add` skips `_checkout_ref` and installs from the wheel. `list`/`enable`/`disable`/`run` unchanged.
2. **Server is global; the target is per-project.** One installed server serves every project. The target declaration lives in the project's `.codeanvil/project.yaml targets:` block; the launcher resolves the project root at start-up (exactly as marconi resolves `MARCONI_WORKSPACE: {project_dir}` in `launch_spec`), and the server reads that project's targets and the key paths under `~/.codeanvil-config/hil/<target-id>/`. So: **server install = global, project wiring = per-project config files, target + keys = per-project state + global key store** — three layers that compose through the launcher, no absolute paths baked anywhere.

### Venv and lock — keep the per-server model, change only the source

**How it works today (confirmed in `src/codeanvil/init/mcp.py`):** each MCP server gets **its own venv and its own lock**, isolated at `~/.codeanvil-config/mcp/<name>/.venv`. `install_mcp_server()` → `_checkout_ref()` (git clone to the server's dir) → `_build_venv()` runs `uv sync --directory <dest>` against *that server's* `pyproject.toml`/`uv.lock`. A server that declares `system_packages` (marconi → gnuradio) builds on the OS interpreter with `--system-site-packages`; one that declares none gets a plain venv on uv's chosen Python (`_target_interpreter()` returns `None`). This is independent from the shared **methodology runtime** venv (`~/.codeanvil-config/runtime/`, its own `uv.lock` seeded from the shipped `RUNTIME_SPEC_DIR/uv.lock`), which exists for skill scripts via `codeanvil python`, not for MCP servers.

**Decision for `vsil_hil_mcp`: keep own venv + own lock.** It needs the MCP SDK (like marconi's `--extra mcp`), so isolate and pin it exactly like any other server. The model already exists and works.

The only deltas vs marconi:

1. **Source is the wheel, not git.** marconi is `git clone` + `git checkout <ref>`; `vsil_hil_mcp` is bundled → `mcp add` **copies** its source from the installed wheel (`templates/mcp/vsil_hil_mcp/`) into `~/.codeanvil-config/mcp/vsil_hil_mcp/`, then the **same** `_build_venv()` runs `uv sync --directory`. Its `pyproject.toml` + `uv.lock` ship inside the wheel — exactly the parallel the methodology runtime already uses (`RUNTIME_SPEC_DIR/uv.lock`). So the "pin" is the shipped lock + the CodeAnvil wheel version, bumped per release → automatic version parity, no git `ref`.
2. **No `system_packages`.** It is a pure ssh/rsync proxy that shells out to the system `ssh`/`rsync` **binaries**, so it needs no heavy Python deps and no `--system-site-packages` — a small, plain venv. `_target_interpreter()` returns `None`.

Follow-ups this creates (T3): `_checkout_ref` grows a `source: bundled` branch (copy-from-wheel instead of clone); `server_rows()`/`mcp list` needs a bundled-aware "pinned/version" signal (no git HEAD — show the wheel version or lock hash instead).

### HW init reuses the existing collector — no vendoring

`init_codeanvil()` emits a human-run Linux provisioning script. It installs CodeAnvil
from the **same release tag** as the host, checks `--version`, then runs `codeanvil init`
and `codeanvil runtime sync`. psutil belongs to CodeAnvil's own environment; the collector
runs as `codeanvil telemetry`. SDR libraries and project dependencies are separate setup
steps, not bundled into the methodology venv. Windows provisioning is not implemented.

**Blocking sub-gap → Phase 0 refactor (R0).** Today `run.sh` calls `codeanvil python templates/skills/S2_implement_services/scripts/telemetry_collector.py --pid $$` — a repo path that only resolves in a scaffolded project through the skill copy, and is fragile on the target. The collector is a loose script *under the S2 skill*; it should be a first-class CodeAnvil subcommand. **R0 (below) moves it to `codeanvil telemetry <flags>`, in-process, with psutil as a CodeAnvil dependency.** Then `run.sh` calls `codeanvil telemetry …` identically on host and target — no path, no `codeanvil python` indirection. R0 is a prerequisite for the HIL work and independently fixes the existing fragility.

## Dependency layers, provisioning, and privilege

**Three dependency layers on the target — never mixed** (this *is* the "separar dependencias" David asked for):

1. **Tool + methodology runtime** — `codeanvil` (uv tool install, including psutil/collector) plus `~/.codeanvil-config/runtime/.venv` for skill scripts. The collector runs in the tool environment as `codeanvil telemetry`; `codeanvil python` runs standalone methodology scripts.
2. **Project venv** — the project's own `pyproject.toml`/`uv.lock`, built with `uv sync --frozen --no-dev` in the workspace. The DUT runs via `uv run <package>`. Delivered code never imports the tool (existing hard rule).
3. **OS system packages** — SoapySDR / rtl-sdr / hackrf libs, bridged into whichever venv needs them via `--system-site-packages` (the existing `system_packages` + `install_hint` machinery).

**Per-project provisioning = one idempotent bootstrap.** `init-hil` chains: install codeanvil → `runtime sync` → project `uv sync` → OS system packages. Re-runnable; resumes.

**Privilege model — NO autonomous high-privilege install tool.** This is the tension to resolve explicitly. Split by privilege:

- **Project deps** (`uv sync`, user-owned workspace): **ALLOW via `ssh_exec_cmd`** — no sudo, the agent does it freely.
- **OS packages, udev rules, anything sudo**: through **`ssh_exec_cmd_trusted`** — the agent drafts the exact command (it can build it with `install_hint(package, os_family)` from `system_packages.py`), the runtime's prompt on that distinct tool is the human's approval, the server runs it under the target's `hil_policy`. No tool installs OS packages silently on its own — that would violate P1 (mutating the target is consequential → HITL).

**HW debugging — diagnose yes, fix gated.**

- **Diagnose (read-only, ALLOW):** `lsusb` (is the SDR enumerated?), `dmesg | tail` (USB / undervoltage), `SoapySDRUtil --find`, `rtl_test`, `vcgencmd get_throttled` (RPi throttle/undervolt), the device probe. The agent is genuinely strong at reading these — this is real value.
- **Fix (ASK or human-only):** driver reinstall, udev rules, group membership (`plugdev` for non-root USB), firmware. **Physical** faults (antenna, USB power, RF environment) are human-only — the agent names the symptom, cannot fix them. This keeps the model out of the physical/real-time loop (paper principle).

Gotcha flagged: non-root access to RTL-SDR/HackRF needs udev rules + the confined user in `plugdev` — a one-time **ASK** provisioning step, never autonomous.

## Fit with VL-1 and VL-2

The target is only *where* `run.sh` executes; the VL semantics are unchanged, and the VERIFIED (VL-0/VL-1) vs VALIDATED (VL-2) honesty is preserved.

### VL-0 / VL-1 on the target = PIL, still VERIFIED

S2/G2 **branch on whether a remote target is declared.** Remote: `ssh_exec_cmd("cd <ws> && verification/run.sh vl1")` via the MCP, then `fetch_evidence()` pulls the telemetry back. Local (PC→SDR): the agent runs `verification/run.sh vl1` directly — no MCP, telemetry is already on the host. Either way it is the same tests, Mock HAL, synthetic I/Q and `SYS-*` thresholds, but **on the real processor**, with the collector sampling that UC's CPU/temp/throttling. New value: the §1.7 telemetry envelope is measured against the real UC. `test_run.md` gains a **target block** (host, os, arch, CodeAnvil version, device); the environment line names the UC, not the dev box. When a remote target is declared, G2.0/G2.1 run on it through the proxy and the honesty declaration names the UC. Still VERIFIED — no real RF.

### VL-2 on the target = HIL — infra necessary but not sufficient

| VL-2 piece | Supplied by this infra? |
|------------|-------------------------|
| Real HW HAL (`hal/real.py`) against the SDR | **No** — delivered code (S2). The infra carries and runs it. |
| Device probe + capability guard | **No** — delivered code; exposed via `ssh_exec_cmd("codeanvil python -m <pkg>.hal.probe")`; out-of-range `configure` rejected before the SDR. |
| **Oracle** (reference signal) | **No — OPEN.** calibrated source / HackRF loopback / known OTA, declared in SyRS §6 `PROTO-*`. Phase 2 blocker. |
| Correction chains + uncertainty (SyRS §4/§5) | **No** — GT; mandatory in `mock+real`. |
| Machine measurement record | **Yes, enabled**: `run.sh vl2` writes `measurement.json` (raw, corrected, u, device metadata, capture SHA) into `verification/telemetry/`, fetched back; G2.2 ingests the file, the human judges, the LLM never fabricates a measurement. |

The real upgrade this infra delivers: VL-2 goes from "human pastes numbers" to "machine captures, human judges" — **but it does not make VL-2 claims valid on its own.** The oracle + corrections are a separate workstream (delivered code + GT). SDR TX (HackRF loopback) is in the ASK tier = the P1 HITL barrier.

**Durability contract (robustness vs HW faults, not false atomicity).** Telemetry is a sampled, append-only, loss-tolerant evidence log — *not* a config file, so tmpfile+rename atomic-replace is the wrong pattern (it would mean rewriting the whole file each sample). The contract instead:
- **Writer:** whole-line write + `flush` per sample (already done); `open("w")` once then append, never rewrite history → a crash can only affect the tail, never prior samples; one file per run (timestamp+pid), no resume-clobber; sensor glitches write `{"unavailable": reason}`, never a false zero.
- **Reader (G2 / verifier / analysis):** must **tolerate and skip a torn trailing line** — a power cut mid-write can leave one partial last line; everything before it is intact.
- **Non-fatal:** a telemetry write failure (`ENOSPC`, SD remounted read-only — classic dying-card modes) must **degrade, not abort the verification run** (the collector is a background companion).
- **`--fsync` optional, default off:** `flush` reaches the kernel page cache, not the flash; `fsync`-per-sample survives a power cut up to the last line but costs SD wear and stalls, and buys little here (a power cut means the run failed and is re-run). Offer it as an opt-in flag for forensic cases; do not default it on.

0 · The big picture

V-SIL v3 is a function with one input and two possible outputs. It never edits its input: when the Build Package cannot be met on the declared COTS hardware, it returns an RFD and waits.

1 · Terminology used in the diagrams

A short reference for the terms used across the diagrams. V-SIL term marks a name this methodology defines itself; the rest keep their usual meaning, and any difference is stated.

Lifecycle

Stage / gate
A stage produces work; a gate decides whether it moves on, as in Stage-Gate. Gate verdicts here are PASS, FAIL or RFD.
Sub-gate
V-SIL term. G2.0, G2.1 and G2.2: the parts of G2 that fire for the declared level.
HITL
Human-in-the-loop: a person makes the decision at that step. Gate H is the human authorisation after G0. Not to be confused with HIL.
Build Package
V-SIL term. The input: PRD (product requirements document), COTS envelope, acceptance criteria, lab procedures, calibration and tolerances.
COTS
Commercial off-the-shelf: hardware bought as is, whose limits the design must accept.
Defect
The requirements are achievable but the design or a module is wrong. Fixed inside V-SIL.
RFD
Request for Deviation: a formal request for a planned departure from a requirement; an unplanned one is a waiver (ECSS-M-ST-40C). V-SIL raises it when the COTS platform cannot meet the requirements. Unlike ECSS departures, it ends in an updated Build Package.
Verified Prototype
V-SIL term. The output: the built system with evidence per module and path.
FW-*
V-SIL term. Future work register entry: a proposal for a later version, never a way to defer a current criterion.
MLOps
Machine learning operations: an automated model lifecycle covering training, versioning and deployment. Future work here (FW-005).

Requirements

GT
Ground Truth: the StRS + SyRS pair that defines what "correct" means.
IEEE 29148
The requirements engineering standard that supplies the document blueprints.
StRS
Stakeholder Requirements Specification (§9.4 of the standard).
SyRS
System Requirements Specification (§9.5 of the standard).
STK-*
Stakeholder requirement block.
NRM-*
Normative obligation block, citing its standard and clause.
HWC-*
COTS hardware constraint block.
SYS-*
System requirement block; it must trace back to StRS blocks.
Deterministic
The same input always gives the same verdict: g0_validate.py, with no AI.
Verification
Objective evidence that specified requirements are fulfilled: built right (ISO/IEC/IEEE 15288).
Validation
Objective evidence that the requirements for the intended use are fulfilled: the right thing built (ISO/IEC/IEEE 15288). This page keeps VALIDATED for real-hardware evidence.
Honesty declaration
V-SIL term. The statement of which environment backs each claim.

Architecture

Service
An independently deployed unit with its own base and modules, such as SVC-EDGE.
Base layer
What a service builds first: orchestration, HAL and data routing.
Module
A unit of function with its own verification profile.
Verification profile
A module's declared fields, including hw_dependency and required_vl.
DAG
Directed acyclic graph of build dependencies. A runtime message loop between services is reviewed separately and is allowed.
Interface contract
What crosses an edge: type, schema version, units and latency.
Service contract
A versioned contract between services, with failure behaviour, such as occupancy.v1.
PATH-*
A named end-to-end route that carries a cross-service requirement.
HAL
Hardware abstraction layer: a uniform interface that hides hardware details from the software above it.
Mock HAL
V-SIL term. A software signal generator behind the HAL port. In test-double terms it is closer to a fake than a strict mock.
Real HW HAL
V-SIL term. The production HAL that drives the declared COTS SDR.
ML package
V-SIL term. An optional model input to a module, trained with Mock HAL data plus labels or, failing that, Real HW HAL data plus labels. Uncertain: its S2 and G2 integration is future work.
UC
Compute unit: the machine that runs the system under test.
Telemetry companion
V-SIL term. A process beside each test that records UC state; verification infrastructure, not a module.
Flowgraph
A GNU Radio signal-processing graph. A hierarchical block groups blocks into one, and here represents a module.

Testing

Unit test
Tests one module or base part in isolation.
Test double
Any stand-in that replaces a production part during a test (Meszaros).
Stub
A double that gives canned answers to the unit under test.
Driver
A routine that calls the unit under test and feeds it test cases.
Fake peer
A working but simplified stand-in for the other service.
Top-down
Integrates from the base downward, with stubs for missing modules.
Bottom-up
Integrates from modules upward, with drivers in place of missing callers.
Sandwich
Hybrid of top-down and bottom-up, so it uses both stubs and drivers.
Contract test
Checks each side of an integration in isolation against the shared contract.
Golden vector
A versioned input with its known expected output, used as a benchmark. Changing one invalidates the evidence that used it.
Evidence record
V-SIL term. A test result with its level, environment and UC readings.

Verification levels

VL-0 / VL-1 / VL-2
V-SIL term. Nested levels: logic, simulated system, real hardware. There is no single standard scale for these.
Floor
VL-0 for every module, contract and path in every cycle.
SIL
Software-in-the-loop: the real code runs on a host against a simulated environment.
PIL
Processor-in-the-loop: the code runs on the target processor with a simulated environment. Not a V-SIL level yet (FW-002).
HIL
Hardware-in-the-loop: real hardware under test, classically against a real-time simulated plant. VL-2 goes further and uses real RF.
HAL substitution
Swapping the HAL behind the same port to move between levels.

Radio and signal processing

RF / SDR
Radio frequency; software-defined radio, which turns RF into samples for software to process.
I/Q
In-phase and quadrature samples: one complex number per sample, as in raw_iq.
MS/s
Million samples per second.
DSP
Digital signal processing.
FFT / bin
Fast Fourier transform; a bin is one frequency slot of its output.
PSD
Power spectral density: signal power per frequency, here averaged over FFTs.
SNR
Signal-to-noise ratio, in dB.
Pd / Pfa
Probability of detecting an occupied channel; probability of calling an idle one occupied. They trade off.
dBFS
Level relative to digital full scale (0 dBFS). Not an absolute power.
dBi
Antenna gain relative to an isotropic radiator.
Screening grade
V-SIL term. The development team's own calibration quality: useful for screening, not normative.

2 · Stage-gate overview

Three stages (S) do work; three gates (G) decide. Each gate sends work forward on PASS or back to the stage that can fix it; S1, G1 and G2 can also raise an RFD. Click any node to see what it consumes, produces, who decides, and where it routes.

Governing principles

P1HITL is an authorisation barrier; HIL is a validation barrier. A human saying "go" (Gate H) is not evidence; real hardware results (VL-2) are.
P2Oracle ≠ generator: the model never approves its own work [7]. Whoever writes the code is not the one who passes it.
P3G0 is the only deterministic gate: its mechanical rejection beats any approval [8]. Every other gate verdict is human (HITL).
P4Verified ≠ validated: every claim names the environment it was produced in [9] (see the honesty declaration in §10).

3 · S0: Normalisation and Ground Truth

S0 is a casting step, not a review: it pours the Build Package into the IEEE 29148 [12] blueprints and makes no judgement about sufficiency or scope. Any iteration happens later, at G0.

4 · G0: Structural validation

Deterministic, no AI, binary verdict: g0_validate.py runs four families of checks over both documents and exits 0 or 1. Only after a PASS does the human Gate H ask: requirements complete, bounded, and verifiable?

5 · S1: System of layered services

S1 allocates one Ground Truth to one or more services. Each service has its own base and modules. Independently deployed services meet through versioned contracts; a requirement spanning them has a named end-to-end path.

5.1 Two service stars: edge + UI

Each star has a local base at its center and modules on its spokes. Select a flow to see which contract crosses the service boundary, and drag a node to rearrange the graph. The two directions are a valid runtime interaction loop; implementation still follows an acyclic order: contracts, service bases, modules, then system integration.

5.2 Layered architecture inside each service

Within each star, S1 produces three layers. They are also the local order of construction in S2: base layer first, then modules, then the integrated service.

5.4 Optional supplied ML model

Status: uncertain. This version defines the model only as an optional S1 input and a G1 readiness check; its connection to S2 and G2 is future work (FW-005). When a design chooses ML, the model is an optional input to a module. It is trained with Mock HAL data plus labelling or, failing that, with Real HW HAL data plus labelling. S1 records weights and hash, training data source and labelling, inference inputs and outputs, preprocessing, performance metadata with its evaluation conditions, and COTS resource budgets. G1 checks that this package is ready to implement. G2 measures the actual model in the integrated system; supplied performance figures are prior evidence. Automating this lifecycle with MLOps is future work (FW-005). The star toggle above shows an illustrative alternative; the terminal example below uses no ML model.

5.5 HAL substitution ladder and telemetry companion

S1 designs two HAL implementations behind one base-layer interface contract. They differ only in what produces raw_iq; swapping them is the HAL substitution that moves between verification levels [11]. S1 also specifies a telemetry companion that runs beside every test. Pick a level to see what feeds the port.

6 · G1: Service, dependency, and contract validation

G1 asks: are all implementation-critical design choices resolved? The five core checks remain. Two system checks cover service boundaries and end-to-end requirements; two more cover the HAL substitution ladder and the telemetry companion. The S1/G1 template expands these families into twelve general review items and one conditional ML item. A runtime message loop is reviewed as a protocol; only the implementation dependency graph must be acyclic.

1 · DAG acyclicity

FM design: all edges point downstream ✓

2 · Interface completeness

Every edge must carry a typed contract.

3 · Coverage

Every SYS-* reaches a module or a named path across services.

4 · Stub feasibility

If you cannot write a deterministic stub from the contract, it is incomplete.

5 · Profile consistency

Hardware-dependent modules must be planned for HIL.

6 · Service boundary

Every service has a deployment target, state owner, and ports. Every runtime exchange has a versioned contract with timeouts, retries, and disconnect behavior.

Edge telemetry and UI commands may form a runtime loop. Their implementation order still starts with the contracts.

7 · End-to-end coverage

A cross-service SYS-* names a path, an acceptance owner, a measurable budget, and a verification environment.

SYS-002: classifier → occupancy.v1 → dashboard.

8 · HAL substitution ladder

Mock HAL and Real HW HAL expose the same base-layer interface. Golden vectors carry digest, generation parameters, and expected outputs.

The Real HW HAL references the Build Package's laboratory procedures, calibration grade, and tolerances.

9 · Telemetry companion

The spec declares what it monitors, its sampling interval, and its resource budget.

Its footprint is bounded below a declared threshold, so it cannot disturb the system under test.

Optional · supplied ML package

When a module uses ML, G1 checks the weights, identity, training data source and labelling, inference contract, evaluation metadata and COTS budget.

No ML module → no model box or ML check. Missing required package → FAIL; demonstrated COTS infeasibility → RFD.

PASS → S2  ·  FAIL → S1  ·  RFD if infeasible

G1 is a human (HITL) design review, not a deterministic gate. An agent may prepare it and recommend a verdict, including an RFD; the human decides.

7 · S2: Per-service implementation and system integration

Each service builds its base first and proves it top-down against stubs. It then replaces stubs one at a time, in DAG order, proving each module bottom-up with a driver. The stepper shows SVC-EDGE. Once both services pass locally, producer and consumer contract tests and connected-service path tests complete VL-0. Step through it.

Future work (FW-005). If an ML module exists, S2 builds its inference adapter against a deterministic fake response for VL-0 integration, then uses the identified model weights for tests that claim model behavior.

Golden vector governance

Each golden vector or synthetic capture used by the Mock HAL is a controlled artefact: unique identifier, SHA-256 digest, generation parameters, the condition it simulates (nominal, edge-case, degraded), and the expected output at the consuming module's contract. Changing a vector invalidates every evidence record that used it. The set is versioned alongside the source code.

8 · G2: Adaptive verification gate

8.1 Verification levels nest

Each level contains every test of the levels below it. In the FM flowgraph, moving up a level means swapping what feeds raw_iq: the HAL substitution ladder mock → SIL → HIL [11], with the Mock HAL at VL-0 and VL-1 and the Real HW HAL at VL-2. The telemetry companion runs at every level.

8.2 Adaptive rule: pick a scenario

The user chooses a level per module and system path, per cycle. The floor covers every module, service contract, and cross-service path at VL-0. Evidence may claim only the environment tested. Every evidence record includes the companion's readings; evidence produced while the UC was outside its declared operating envelope is flagged and may be invalidated by the reviewer. The matrix shows module choices; the edge → UI path has its own S1 required_vl and evidence.

Future work (FW-005). For an ML module, G2 measures the supplied model in the implemented system at the declared level. Performance metadata received in S1 informs the tests; it does not supply the G2 verdict.

9 · Feedback routing

A gate failure is classified before it is routed. A defect (requirements achievable, implementation or design wrong) is fixed inside V-SIL. An RFD (requirements infeasible on the declared COTS platform) leaves V-SIL: it suspends until the Build Package is updated and re-enters at S0. Pick a failure to see its route.

9.3 RFD-001 as a trade-off chart

The paper's RFD example: two measured FFT configurations against two requirements. The green box is where both STK-007 (latency ≤ 100 ms) and STK-012 (Pd ≥ 0.95 @ 10 dB) hold. Neither measured point is inside it, which is exactly what makes this an RFD and not a defect. Toggle an option to see the relaxed region.

9.4 Defect vs RFD

Defect

Requirements achievable · implementation or design wrong · fix inside V-SIL (to S1 or S2).
Self-diagnosis: a module that was not changed fails on re-test → undeclared dependency → design defect → S1.

RFD

Requirements infeasible · the COTS platform cannot deliver both · Build Package must change. Contents: conflicting requirements, evidence with its VL, trade-off options, impact analysis, recommendation (ECSS [16], MIL-HDBK-61A [17], NASA NPR 7150.2 [18]).

10.1 Optional future work register

After G2, the report may list proposals for later software versions. Each entry names its origin, evidence, candidate version, decision owner, dependencies and proposed acceptance criterion. The register is absent when there are no proposals. The Build Package author decides whether a proposal becomes input to a later S0/G0 cycle. A current SYS-* that fails still follows the defect or RFD route.

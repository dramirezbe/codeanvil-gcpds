V-SIL v4: Agile-V Stage-Gate Lifecycle, diagram by diagram

Eight-node stage-gate chain S0→G0→S1→G1→S2→G2→S3→G3. S2 decomposes the design into self-contained PLAN.md per module with topological slicing; S3 implements each module in fresh context. Verification is adaptive per module with a mandatory VL-0 floor. Report-driven gate chain with stale detection. HAL substitution ladder and telemetry companion tie every claim to its data source and compute-unit state.

0 · The big picture

V-SIL v4 is a function with one input and two possible outputs. It never edits its input: when the Build Package cannot be met on the declared COTS hardware, it returns an RFD and waits.

1 · Terminology used in the diagrams

Lifecycle

Stage / gate
A stage produces work; a gate decides whether it moves on. Gate verdicts: PASS, FAIL or RFD.
Sub-gate
V-SIL. G3.0, G3.1 and G3.2: the parts of G3 that fire for the declared level.
HITL
Human-in-the-loop: a person makes the decision. Gate H is the human authorisation after G0.
Build Package
V-SIL. The input: PRD, COTS envelope, acceptance criteria, lab procedures, calibration and tolerances.
COTS
Commercial off-the-shelf hardware whose limits the design must accept.
RFD
Request for Deviation: planned departure from a requirement (ECSS). V-SIL raises it when the COTS platform cannot meet the requirements.
Verified Prototype
V-SIL. The output: built system with per-module and path evidence.
PLAN.md
V-SIL. Self-contained module specification from S2: scope, contracts, traced reqs, tasks, verification plan, delta traceability, risks.
INFRA-PLAN.md
V-SIL. Slice 0 plan: base layers + verification kit, distinct from module PLAN.md.
Agile-V
Module as the iteration unit: each runs a mini-V cycle (plan → implement → verify) [19a][19b].
Topological slicing
Ordering modules by S1's dependency graph into slices: lower layers first.
Fresh context
V-SIL. Each module enters S3 with only its PLAN.md and contracts it touches. No accumulated state.
Living GT delta
V-SIL. Per-module ADDED / MODIFIED / REMOVED / RENAMED. OpenSpec [21] scoped to module boundary.
Stale detection
V-SIL. A report is stale when any declared input has changed since the report was produced. Gates reject stale reports.
Report-driven
V-SIL. Each stage writes a report; each gate reads it. No re-derivation; accountability chain.
Draft mode
V-SIL. S0/G0/G1 enter draft automatically when unresolved items exist; cannot advance until resolved.
Failure triage
V-SIL. Machine or gate failures are translated before reaching the human, with concrete reconciliation options.

2 · Stage-gate overview

Four stages do work; four gates decide. S2 and G2 are the agile planning layer. Each gate sends work forward on PASS or back to the stage that can fix it. G3 has five routing classes including plan defect → S2. Click any node to see what it consumes, produces, who decides, and where it routes.

Governing principles (P1–P8)

P1HITL is an authorisation barrier; HIL is a validation barrier.
P2Oracle ≠ generator: the entity that verifies never approves its own work [7].
P3G0 is the only deterministic gate: its mechanical rejection beats any approval [8]. G2 and G3 are agent-prepared, human-approved.
P4Verified ≠ validated: every claim names the environment [9].
P5Module is the iteration unit — Agile-V [19a][19b] with module-level mini-V cycle.
P6Layers are orthogonal to iteration — layered architecture is a structural invariant.
P7Fresh context per module — only PLAN.md and contracts it touches.
P8Living GT with delta traceability — ADDED/MODIFIED/REMOVED/RENAMED per module [21].

3 · S0: Normalisation and Ground Truth

S0 is a casting step, not a review: it pours the Build Package into the IEEE 29148 blueprints and makes no judgement about sufficiency or scope. Any iteration happens later, at G0. Following SDAD Phase 1 (spec crystallisation) [6].

4 · G0: Structural validation

Deterministic, no AI, binary verdict: g0_validate.py runs four families of checks and exits 0 or 1. Only after a PASS does the human Gate H ask: requirements complete, bounded, and verifiable?

5 · S1: System of Layered Subsystems with Module Decomposition

S1 allocates the Ground Truth to subsystems, designs layered architecture within each, and decomposes modules with their dependency graph. The hierarchy is system → subsystem → module. Each module carries a full identity block: module_id, subsystem_id, layer, depends_on, provides, hw_dependency, required_vl, traced_reqs.

5.3 HAL substitution ladder and telemetry companion

S1 declares HAL mode: mock-only or HAL mode: mock+real. Both HALs sit behind one base-layer interface contract. The telemetry companion is mandatory in every design and every test run. Pick a level to see what feeds the port.

6 · G1: Design Review (12 checks + 1 conditional)

G1 asks: are all implementation-critical design choices resolved, and is every module identifiable and plannable? Human HITL review — the agent prepares, the human decides. The agent reads the whole design and GT, re-derives every check from source sections, and runs the declared toolchain.

1 · Subsystem topology

Every subsystem: one responsibility, deployment target, state owner, declared ports. Network and COTS envelope support the topology.

2 · DAG acyclicity

No dependency cycle within or between subsystem build units. Runtime message loops reviewed for bounded behavior.

3 · Interface completeness

Every internal edge has a typed contract; every cross-subsystem exchange has a versioned contract with failure behavior.

4 · Coverage

Every SYS-* traces to module(s) or an end-to-end path, with owner and measurable acceptance evidence.

5 · Stub feasibility

Every contract is complete enough to write a deterministic stub or fake peer.

6 · Verification-profile consistency

hw_dependency: true → required_vl: VL-2; system paths have a declared level and environment.

7 · HAL substitution ladder

Mock HAL exposes the base-layer interface; golden vectors carry digest, parameters and expected outputs. In mock+real, Real HW HAL references SyRS PROTO-*.

8 · Telemetry companion

Declares what it monitors, sampling interval, resource budget, footprint bounded below threshold.

9 · Supplied ML model (conditional)

Weights, metadata, training data, labelling, inference contract, COTS budget. Omitted when no ML model.

10 · Toolchain availability

Language runtime and package manager of every Toolchain entry answer their version command on the dev machine.

11 · Module decomposition

Every module has all identity fields. Every SYS-* in the GT appears in at least one traced_reqs. No empty traced_reqs.

12 · Topological slicing feasibility

The DAG admits a topological sort. Every depends_on points to modules or base-layer contracts available before the module is scheduled.

PASS → S2  ·  FAIL → S1  ·  RFD if infeasible

7 · S2: Module Planning (Agile-V Layer)

S2 takes the G1-validated design and produces a PLAN.md per module (or INFRA-PLAN.md for Slice 0). The backlog is ordered by topological slicing of S1's dependency graph. Each plan carries a living GT delta (ADDED / MODIFIED / REMOVED / RENAMED).

8 · G2: Module Plan Micro-Gate

G2 validates each PLAN.md before the module enters S3. Lightweight by design: G1 did the full review; G2 checks only that the plan is self-contained, traceable, and buildable. Runs once per module.

9 · S3: Per-Module Implementation and System Integration

Each module enters S3 in fresh context (P7): PLAN.md + contracts + base-layer API + verification kit + stubs. The context does NOT carry: full system design, complete GT, other modules' source code, or accumulated state. Step through the sandwich integration.

10 · G3: Adaptive Verification Gate

10.1 Verification levels nest

10.2 Adaptive rule: pick a scenario

The user chooses a level per module and system path, per cycle. Four constraints: floor (VL-0 always), honesty (claim ≤ environment tested), telemetry context (outside envelope → flagged), HAL mode ceiling (mock-only caps at VL-1). G3 runs the tests S3 wrote and writes none; runs in a separate verifier context (P2).

11 · Feedback routing (5 classes)

G3 failures are classified into five outcomes. An operational problem (DUT/environment) is fixed on the target and G3 re-run. A defect is fixed inside V-SIL. An RFD suspends V-SIL until the Build Package is updated. Self-diagnosis: if a module that was not changed fails → undeclared dependency → design defect → S1. Pick a failure to see its route.

Operational fix

DUT/env problem (SSH, udev, permissions). Fix target, re-run G3.

Design defect → S1

DAG undeclared dependency; contract incomplete. Self-diagnosis: unchanged module fails → S1.

Plan defect → S2

PLAN.md omitted contract; verification plan missing level; task ordering violated.

Module defect → S3

Processing output wrong; deserialisation bug.

RFD

Requirements infeasible on COTS. Build Package must change.

12 · Failure triage and draft mode (S0 · G0 · G1)

V-SIL v4 softens the loop, not the checks, through two devices scoped to S0, G0 and G1 — never to S2, S3, or G3.

Failure triage

Every G0 ERROR, missing-list placeholder and G1 open finding is translated before it reaches the human. The agent describes each requirement by what it asks (block ID in parentheses) and offers 2–4 concrete reconciliation options. The human chooses; the agent applies. The verdict stays the validator's exit code (G0) or the human's answer (Gate H, G1).

Draft mode

When a requirements stage finds unresolved items, it enters draft automatically and cannot advance until each one is resolved. Mechanical fixes (removing scaffolding, filling a stated value, dropping broken references) are auto-applied and reported. Judgment calls go to the human: fix, ignore/accept (recorded with decider's name), or escalate to RFD. On commit — all items decided — one recorded run is written.

13.1 Future work register

FW-001 · CI/CD automation of G3 evidence

A pipeline reproduces declared G3 checks and links reports to cycle and source revision.

FW-002 · PIL as a full G3 sub-gate with timing/scheduling checks

Currently PIL is a declared mode; a dedicated G3.PIL sub-gate is not yet defined.

FW-003 · Formal fault injection at VL-2 (ISO 26262-5 §10)

Current VL-2 tests nominal operation only. Fault scenarios per module.

FW-004 · SIL ↔ HIL correlation measurement

Quantified deviation between Mock HAL and Real HW HAL results for overlapping test cases.

FW-005 · MLOps for the optional ML model (S3/G3 integration)

Pipeline reproduces training from versioned data and links each model version to its G3 evidence.

FW-006 · Automated PLAN.md generation from S1 design

Reduce manual S2 effort for large module counts.

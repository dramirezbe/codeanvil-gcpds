Engineering AI Agent Harnesses

A visual guide to the architectural paradigms, ownership boundaries, and verification strategies for building reliable agent systems.

Agent = Model + Harness

Based on the paper by David Ramírez-Betancourt · Universidad Nacional de Colombia · v2.1

The Four-Layer Stack

The model is rented. The cockpit is rented. The harness is owned. The stacking order is also a dependency order: higher layers depend on lower layers, but never the reverse.

L3

Domain Governance Owned

Ground truth, Rule D validators, standards, custody

The field's invariants — what counts as correct in your domain. A requirement that must trace to its source, a schema that stays backward-compatible, a dose inside a range. This layer holds the deterministic validators, the standards, and the cryptographic custody chain. It survives every change of model, cockpit, and personnel.

L2

Methodology Harness Owned

Skills, gate DAG, reports, verdicts

The procedures that encode how work is verified. Skills packaged as runtime-agnostic directories, an ordered gate topology (a DAG of verification stages), append-only reports per gate and cycle, and a verdict protocol where only PASS and FEEDBACK exist — no DENIED.

L1

Cockpit Rented

Loop, tools, permissions, streaming, diffs, compaction

The commercial coding agent — Claude Code, Codex CLI, OpenCode, Pi. The interface where a human and a model collaborate. It owns execution, tool dispatch, streaming, permission prompts, diff rendering, context compaction, and model routing. These are solved products with years of edge cases — rebuilding them is maintenance, not differentiation.

⟁ Terminology note
This paper uses cockpit for the rented agent runtime layer. The broader field adopted different terms for the same concept:
Cockpit (this paper) = Builder harness (Böckeler / Thoughtworks, Apr 2026) = Inner harness = Agent runtime (Microsoft Build 2026)
Conversely, this paper's Outer harness maps to Thoughtworks' User harness.
Note: "harness" is polysemous in the field — it may denote the whole product (inner + outer) or just the user's layer, depending on source. Red Hat frames a five-layer matryoshka (Infrastructure → Sandbox → Harness → Runtime → Model); Thoughtworks uses concentric rings (Model → Builder harness → User harness).
M

Model Rented

Weights — interchangeable, no memory of the project

The language model itself. Rented weights that improve on the vendor's schedule. Interchangeable — the harness does not depend on any specific model. The model is confined to synthesis: producing artefacts that validators and humans will judge.

Three Conflations That Cause Failures

Capability Conflation

Assuming a better model will fix a broken workflow. It won't — whether a requirement traces to a system requirement is a property of the document, not of the prose.

Layer Conflation

Assuming that building an agent means building its environment. The streaming renderer, the diff applicator, the permission prompt are already products.

Ownership Conflation

Assuming a vendor can ship a harness. A vendor ships a runtime and a tool protocol — it cannot ship your domain's acceptance criteria.

The ETCSLV Ownership Split

Meng et al. decompose an agent into six concerns. Three are runtime and belong to the cockpit; three are durable and belong to the outer harness. Confusing the two is the mechanism behind layer conflation.

Concern Cockpit (Rented, Runtime) Outer Harness (Owned, Durable)
Execution Agent loop, tool dispatch, streaming, interruption Which steps run, in what order, and what exit criterion closes each
Tools Tool transport, MCP client, permission prompts Declarative server definitions; capability policy per gate
Context Window management, compaction, injection What must be loaded: the procedure, the baseline, the prior reports
State Session transcript, resumption Gate state, append-only reports, cycle identity, baseline pointers
Lifecycle Session start and stop, model routing Gate order, prerequisites, verdict domain, review mode
Evaluation None beyond rendering a diff Validators, decidability partition, human verdicts

The Seam

The seam is contractual: the cockpit owns everything that must respond within a frame (input, streaming, approval, rendering). The outer harness owns everything that must survive the session (which gate is open, what the last verdict was, what the baseline digest is, who is accountable). The harness treats the cockpit as a function from (prompt, tools, workspace) → (artefacts, transcript), and evaluates only the artefacts.

The Outer Harness Quadruple

An outer harness is defined as H = (M, G, S, C) — four components, deliberately minimal. Anything not in it (a scheduler, a database, a server, a dashboard) is an implementation choice.

M

Methodology

Procedures stated as runtime-agnostic skills. Packaged as SKILL.md directories — YAML frontmatter, Markdown procedure, optional scripts and assets. No runtime API, no execution model.

G

Gate Topology

A directed acyclic graph of verification stages, each with a precondition and a verdict domain. Acyclic, ordered, starting with a deterministic entry gate. Only two verdicts: PASS and FEEDBACK.

S

State Substrate

Durable, append-only records. A manifest (identity + position), a report tree (one file per gate per cycle), and a custody directory. No database, no session store — just files.

C

Custody

Binds baseline inputs to digests and a signed chain of events. Sealing (SHA-256 per file, manifest digest), Ledgering (HMAC-SHA256 signed hash chain). Detects modification and reordering.

The Decidability Partition

The single most consequential decision in the harness: which checks are scripts, which are model+human judgment, and which are not verification at all.

Rule D

Decidability

If a total function over bytes can decide the property — a section is present, an identifier resolves, a schema validates, a digest matches — implement it as a pure script. Exit 0 = pass, 1 = fail, 2 = error. Never ask a model to check what code can decide.

Rule A

Attribution

If the property requires judgment — is the design sound, is the evidence sufficient — it becomes an agent gate that produces a bounded artefact and requests a human verdict. A gate never certifies itself.

Rule H

Human Closure

The verdict is recorded by a named human, in the report, at a named iteration. PASS is an act of accountability, not a measurement. The verdict is committed out-of-band.

Decision Flowchart

The partition is asked per check, not per gate. A single gate can combine a deterministic script (for structure) with a human verdict (for content). The question is always: what kind of evidence does this check produce?

Gates Combine Both Modes

Script + HITL Gate

Deterministic entry

A script checks structure: sections present, identifiers resolve, schema validates, cross-references intact. But a well-structured document can still be wrong. The human reviews the actual content after the script confirms the form is sound.

Script: structure Human: content

Agent + HITL Gate

Pure judgment

No script validator. The agent synthesizes a bounded artefact. The property being checked — is the design sound? is the evidence sufficient? — cannot be decided by code. The human reviews and gives PASS or FEEDBACK.

Agent: synthesis Human: verdict

Why Rule D Is Load-Bearing

Rule D draws the line between what is reproducible and what is accountable. A deterministic check runs as a standalone process — any CI system, auditor, or second harness can re-run it without a model. But Rule D checks form, not content: a script can confirm a section exists but not that it says the right thing. That's why even a gate with a passing script still needs HITL — the script gates the structure so the human can focus on substance. The cheapest token is the one never sent, but the most important verdict is still the human's.

Gate Topology & Choreography

Gates are verification stages in a DAG. Instead of a central orchestrator, each gate enforces its own precondition — choreographed enforcement replaces orchestration.

Gate Properties

Precondition

Predecessor's latest verdict must be PASS. Each gate checks this itself — no central scheduler.

Bounded Artefact

Every gate produces something a human can review in minutes. A gate that takes an hour to review will be rubber-stamped.

Verdict Domain

Exactly two values: PASS and FEEDBACK. No DENIED — a terminal rejection carries no information about what would be acceptable.

Choreographed Gate Chain

Choreographed Enforcement

Each gate skill performs three steps: (1) resolve the active cycle from the manifest; (2) read the predecessor's latest verdict and refuse if it is not PASS, returning the predecessor's name and the unblocking action; (3) run the gate and append exactly one iteration. The refusal string is a literal contract — it names the blocking gate and tells the human what to do. No central scheduler, no coordinator, no orchestrator program.

State Substrate — Three Artefacts, No Database

Manifest

Identity and position: stable identifier, baseline pointers, active cycle. The single source of "where are we."

Report Tree

One file per gate per cycle. Append-only iterations. The latest iteration is the state — no separate status field can disagree.

Custody Directory

Sealed manifest of the baseline and a signed ledger. Integrity evidence that detects modification and reordering.

Six-Phase Blueprint

Ordered by dependency — each phase produces something the next consumes, and each has an exit criterion that can be checked rather than believed.

1

Domain Invariant & Ground Truth

Baseline format, identity rules, deterministic validator, adversarial fixtures.

Choose the baseline format — if the domain has a standard, adopt it. Fix the identity rules, because traceability is decided by identifier namespaces rather than by prose. Write the validator before any procedure and build adversarial fixtures: a missing section, a duplicated identifier, a reference that points nowhere.

Exit: The validator accepts the reference baseline and rejects every fixture with a line number.
2

Gate Topology

Prerequisite graph, entry point, report schema, verdict domain, cycle scoping.

Enumerate verification stages, assign prerequisites, draw the graph. Write refusal strings before the procedures — they are the entire coordination mechanism. Each gate must be reviewable in bounded time.

Exit: A human can walk the chain by hand, and each gate refuses correctly when its predecessor is absent.
3

Verification Partition

Check inventory with exactly one owner per check. Apply Rules D, A, H.

Build a table with one row per check and one column for its owner. The table forces the question teams otherwise skip: "who is accountable when this check passes and the artefact is still wrong?" The division is by decidability, not difficulty.

Exit: No decidable check is model-evaluated; every agent gate ends in a human verdict; no row is unassigned.
4

Runtime Projection & Discovery

Canonical store, projection mesh, instruction convergence, tool manifests.

Package procedures in a runtime-agnostic format, keep one canonical copy, project into each cockpit's discovery path. Render tool manifests from one declaration. State that configuration isolation is not process isolation.

Exit: Two cockpits complete the same gate with no edits to the methodology (the interchangeability test).
5

State Persistence & Integrity

Manifest, append-only report tree, sealed baseline, signed ledger.

Choose durable state and make it boring: manifest for identity, report tree for history, custody directory for integrity. Keep the key out of the repository.

Exit: Tampering is detected; a missing key fails closed; the ledger verifies after an interrupted write; a forged evidence line fails on replay.
6

Ingress Layer

One or more surfaces over the same state, review protocol, attribution rules.

This is the phase teams build first, which is why they rebuild it. With state in files and the protocol in procedures, a surface is a renderer. The decisions here are review mode per gate and attribution.

Exit: A second surface drives a full cycle; every verdict has a named author and an iteration number.

Harness Maturity Model

Five levels of capability. Each adds a property that survives a change of model, cockpit, or personnel. A team can install every component and remain at L1 if acceptance criteria are still implicit.

L1

Prompt Library

Shared prompts. No ordered gates. Acceptance is ad hoc and lives in people's heads.

L2

Versioned Skills

Procedures packaged and reviewed. Invocation is manual. Evidence is partial.

L3

Gated Harness

Ordered gates, explicit prerequisites, report state, deterministic entry gate, human verdicts.

L4

Portable, Custodied

Multi-cockpit projection, sealed inputs, signed ledger, isolation, regression testing.

L5

Continuously Evaluated

Validator-coverage metrics, methodology regression in CI, upgrade path, externally anchored heads.

The Interchangeability Test

Move a project to a different cockpit — different vendor, different terminal, different configuration — in one working day, without editing the methodology, the gate order, the report schema, or the validators. If the reports produced after the move are comparable, the harness passes. Four conditions make it work: runtime-agnostic procedures, converged instruction files, declarative tool configuration, and file-based state with relative paths.

The Decision Rule

If the differentiation lives in the loop, build the loop (framework). If it lives in the acceptance criteria — in the field's notion of a correct artefact — then the loop is overhead, and the harness is the product.
